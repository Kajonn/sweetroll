## Steps executed

1. `POST /dev/signin` (Ada, Bob) → two sessions via the test identity adapter
2. `POST /systems` (blank) → draft created
3. `PUT /systems/{id}/draft` (d20 reference) → saved
4. `POST /systems/{id}/publish` (`1.0.0`) → version published
5. `POST /characters` → character `Aria` pinned to the exact v1 version, revision 1, defaults applied
6. `GET /characters/{id}` → projection 200 with `Cache-Control: private`, ETag `"1-sha256:<checksum>-1.0"`, `X-Resource-Revision: 1`
7. `POST .../fields/ability/set` (15) → revision 2
8. `POST .../resources/health/bump` (down) → revision 3
9. `POST .../actions/check` (`bonus:2`) → normalized roll (one d20, sides 20, output `d20 + fields.modifier + inputs.bonus`), revision unchanged
10. Replay of the roll key → 200 with `reconciliation.replayed: true` and the same `commandExecutionId`
11. Two bumps at the same `expectedRevision` → exactly one 200 (revision 4) and one 409
12. `PATCH .../archive` → 200 (revision 5); a `set` while archived → 409; `PATCH .../recover` → 200 (revision 6)
13. `GET .../activity` → 200 descending: recovered, archived, resource_bumped, action_executed, resource_bumped, field_set, created
14. `POST .../exports` → 200 `application/vnd.sweetroll.character+json;version=1`
15. `PUT /systems/{id}/draft` (breaking v2) → 200; `POST publish 2.0.0` without acknowledgement → 422; with `acknowledgeBreaking: true` → 200
16. `GET /characters/{id}` → still pinned to v1 (explicit proof, step 18 note)
17. `POST .../migration-previews` (map `ability → ability_score`) → 201 with candidate state, drop/default warnings; `POST .../migrations/{id}/commit` → 200 (revision 7); `POST .../migrations/{id}/rollback` → 200 (revision 8)
18. Explicit proof: the sample is captured at step 16 — the character's `systemVersionId` remained `v1Id` after v2 was published, so publication never mutated a pinned character; the pin changed only at migration commit
19. `POST .../ownership-transfer` (to Bob) → 200; old owner `GET` → 404 with `cacheDisposition: "purge"`; old-owner replay of the transfer → 200 with `replayed: true` and `ownerId` still Bob
20. Expired replay window: force the create key's `expires_at` into the past, re-issue the create → 409 with a "replay window" message instead of re-execution

## Discovered production defects fixed during acceptance (minimal)

1. **Authoring publish version-ID mismatch (root cause of `422 invalid_package` on every create):** `authoring.publish` compiled the package with a throwaway UUID while the DB row id was auto-generated, so stored packages' `versionId` never matched the pinned version at `src/systems/runtime.ts` boundary. Fix: `PublishVersionInput` carries `versionId` and the row is inserted with an explicit `id` (`src/systems/implementation/persistence/repository.ts`, `src/systems/authoring.ts`).
2. **Replay beyond `expires_at` re-executed instead of rejecting:** completed command executions past 30 days were replayed (200) and expired create keys surfaced as 500 `UNIQUE` violations. Fix: `claimExecution`/create return `{ status: "expired" }` mapped to `conflict` 409 with a stable "replay window" message, never touching state (`src/characters/idempotency.ts`, `src/characters/index.ts`, `src/characters/persistence.ts`).
