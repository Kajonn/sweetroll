# Sweetroll public API v1

Use `/api/v1` on the Sweetroll HTTP origin. Download the [OpenAPI contract](../contracts/public-api-v1.json)
from `GET /api/v1/openapi.json`. For local development, start the server with
`SWEETROLL_LOCAL_API_TOKENS=1`, sign in, and go to **Account → API tokens**.
Create a token with `systems:read`, `systems:write`, `characters:read`, and `characters:write`
for this walkthrough. Copy the secret when it appears and set `SWEETROLL_API_TOKEN` in your shell.
Use HTTPS for a remote origin. Hosted token issuance depends on real provider sign-in.

## Scopes

A request needs every scope its operation lists in the contract (`x-required-scopes`) and the
caller's current permission on the resource, exactly as in the web app. A write scope includes
read for the same area: `characters:write` also allows every `characters:read` operation, but
read never allows writes. A token holds one to six scopes. Tokens created before the campaign
scopes existed keep their original scopes.

| Scope | Allows |
|---|---|
| `systems:read` / `systems:write` | System drafts, versions, sharing, lifecycle, export and system art |
| `characters:read` / `characters:write` | Every character the account may read or edit in the web app, standalone or attached to a campaign: sheets, entries, art, rolls, pushes, activity, exports, renames, archive and transfer |
| `campaigns:read` / `campaigns:write` | Campaigns, members, invitations, activity, content, item templates, proposals, media, scenes and display pairing |

Creating a campaign character and assigning, claiming or adopting one change both a character
and its campaign, so they need `campaigns:write` and `characters:write`. Reading an attached sheet
needs only `characters:read`. Token management, browser sessions and the display's own
`/displays/...` routes are not part of v1.

## Python quickstart

Run this command from the repository root.

```sh
python3 scripts/public-api-quickstart.py --base-url http://localhost:3000
```

The script validates the example document, creates and publishes a private system, discovers its
writable fields, creates a character with a non-default value, replays the create, and updates and
reads the sheet. The character ID opens at `/characters/{characterId}` in the web app signed in as
the same account. Each fresh run creates a system and character. Use `--document` to submit another
system document. The sample workflow uses an integer field with three distinct valid values.

## curl quickstart

The shell example uses curl and jq. Run it from the repository root with `SWEETROLL_API_TOKEN` set.

```sh
set -eu
base="${SWEETROLL_BASE_URL:-http://localhost:3000}/api/v1"
document=docs/contracts/examples/d20-system-document-v1.json
run="$(python3 -c 'import uuid; print(uuid.uuid4())')"

api() {
  curl --silent --show-error --fail-with-body \
    -H "Authorization: Bearer $SWEETROLL_API_TOKEN" "$@"
}

json() {
  method="$1"
  path="$2"
  api -X "$method" -H 'Content-Type: application/json' --data-binary @- "$base$path"
}

jq -n --slurpfile doc "$document" '{document: $doc[0]}' |
  json POST /systems/validate | jq -e '.valid'

created="$(jq -n --arg key "$run-system" '{name:"D20 System", idempotencyKey:$key}' |
  json POST /systems)"
system="$(printf '%s' "$created" | jq -r '.system.systemId')"
revision="$(printf '%s' "$created" | jq -r '.draft.revision')"
saved="$(jq -n --slurpfile doc "$document" --argjson revision "$revision" \
  '{expectedRevision:$revision, document:$doc[0]}' | json PUT "/systems/$system/draft")"
revision="$(printf '%s' "$saved" | jq -r '.draft.revision')"
published="$(jq -n --argjson revision "$revision" --arg key "$run-publish" \
  '{expectedRevision:$revision, semanticVersion:"1.0.0", idempotencyKey:$key}' |
  json POST "/systems/$system/publish")"
version="$(printf '%s' "$published" | jq -r '.versionId')"

api "$base/characters/creation-options?systemVersionId=$version" | jq '.entities'
created="$(jq -n --arg version "$version" --arg key "$run-character" \
  '{name:"Rowan", systemVersionId:$version, entityDefinitionId:"character", initialValues:{ability:12}, idempotencyKey:$key}' |
  json POST /characters)"
character="$(printf '%s' "$created" | jq -r '.characterId')"
revision="$(printf '%s' "$created" | jq -r '.revision')"
jq -n --argjson revision "$revision" --arg key "$run-edit" \
  '{value:14, expectedRevision:$revision, idempotencyKey:$key}' |
  json POST "/characters/$character/fields/ability/set"
api "$base/characters/$character" | jq '.values'
```

## Create a system and equip a character

- Use `POST /systems` with `name` for a blank draft. To start from an existing
  version, find a built-in starter via `GET /templates` or use an owned version,
  then send `source: { "kind": "clone", "versionId": "…" }`. To import a
  Sweetroll export, send `source: { "kind": "import", "content": "…" }` with
  the exported JSON as a string. All three creation forms take an `idempotencyKey`.
- `POST /systems/{systemId}/preview` compiles an expiring snapshot of the current
  draft. Publication uses the exact saved revision. Use
  `PUT /systems/{systemId}/sharing` with `access` set to `private`, `link`,
  or `public`. `GET /system-versions/{versionId}/export` returns an owned
  published package and its artwork as portable JSON.
- `GET /characters/creation-options` returns the pinned catalog and the slots
  available to each entity. Create a character, then `POST` to its `/entries`
  with an `entryId` UUID, `slotId`, `templateId`, `expectedRevision` and
  `idempotencyKey`. Optional `values` override template defaults. For a
  personal entry, send `templateId: null` and `values` with a `name`.
- `PATCH /characters/{characterId}/entries/{entryId}` moves an entry when
  `slotId` is present and edits its `values` or `quantity` when supplied.
  `DELETE` on the same path removes it. Both require the current character
  revision and a retry key. The sheet returned by `GET /characters/{characterId}`
  includes current entries and their slot IDs.
- A script can also duplicate an owned standalone character or bump a
  resource by one step through the routes in the OpenAPI contract.

Use `GET`, `PUT`, or `DELETE` on the draft template `/image`, character
`/portrait`, or character entry `/image` endpoint to read attachment metadata,
upload or replace, or remove. An upload includes `description`, `contentType`,
and `dataBase64`. The system template uses the current draft revision and
returns the new one. Portrait and entry art use the current character revision
and the separate attachment revision. Read the attachment metadata for its
current revision. Uploads accept PNG, JPEG or WebP up to 5 MiB.

## Campaign quickstart

The campaign script uses two accounts. Create a token with all six scopes for the GM and one with
`characters:read`, `characters:write`, `campaigns:read` and `campaigns:write` for the player.

```sh
SWEETROLL_GM_TOKEN=… SWEETROLL_PLAYER_TOKEN=… \
  python3 scripts/public-api-campaign-quickstart.py --base-url http://localhost:3000
```

The GM publishes the example system and shares it by link, creates a campaign and invites the
player. The player reviews and accepts the invitation, creates a character and adopts it. The
player rolls for the table and replays the roll with the same key. The GM finds the roll in the
activity feeds, shares a note and a template, and approves the player's item proposal. Last, the
GM uploads a map, reveals fog, places a visible and a hidden token and prints a display pairing
code. Enter that code on the table display at `/display`. Image uploads need the deployment's
image scanner; pass `--no-scene` to a local server without one.

## Play, campaigns and scenes

- `POST /characters/{characterId}/actions/{actionId}` executes an action with `inputs`,
  `expectedRevision` and `idempotencyKey`. Send `entryId` for an action granted by an inventory
  entry. Attached characters accept `audience` (`owner_only`, `gm_only` or `campaign`); when it is
  omitted the campaign default applies. Standalone characters accept only `owner_only`. Dice are
  always rolled on the server.
- Rolls from actions with a push policy carry `roll.rollId`. Use it with
  `GET /characters/{characterId}/rolls/{rollId}`, `…/push-options` and `POST …/push`. Other rolls
  return `rollId: null`; the character and campaign activity feeds list their saved IDs where the
  reader may see them.
- `GET /characters/{characterId}` returns `campaign: null` for a standalone character, or the
  campaign ID, controllers, placement generation and return owner of an attached one. A GM sees
  every attached sheet. A player sees the sheets they control. Everyone else gets `404`.
- Invitation tokens appear once, in the issue or rotate response, and are accepted only in request
  bodies. The invitee calls `POST /invitations/review` and then `/accept` or `/decline` with the
  `invitationRevision` and `accessRevision` from the review.
- To put a campaign item on an attached character, read `GET /characters/{characterId}/templates`
  and send the chosen entry's `source` to `POST /characters/{characterId}/entries` with
  `templateId: null`, no `values` and no `quantity`. The sheet stores a snapshot of the item and
  reports the `source` on that entry. Controllers and GMs can place items; GM-only and other
  restricted templates are not offered.
- Content, template and proposal reads are filtered for the caller as in the web app. GM
  previews (`/content-preview`, `/item-template-preview`) are read-only. A command the caller's
  role does not allow returns `403 forbidden`.
- Scene edits (`/fog-edits`, `/tokens`, background replacement) update paired displays through
  their live stream. Displays pair in their own browser with a code from
  `POST /campaigns/{campaignId}/display-codes`; codes expire after five minutes.
  `POST /campaigns/{campaignId}/displays/{displayId}/revoke` ends the display's stream.
- Art and media byte routes (`…/thumbnail`, `…/{fileId}`, `…/original`) accept the same Bearer
  token and respond with `Cache-Control: private, no-store`.

## Revisions, retries, and errors

- Lists default to 25 records and accept up to 100. Pass `nextCursor` as `cursor` with the same
  filters to request the next page. A null cursor marks the end.
- Validation returns `200` with `valid` and diagnostics relative to the submitted document.
  Publication checks the saved revision, asset permissions and availability, and compatibility with
  the latest version. Set sharing with `PUT /systems/{systemId}/sharing` or `PATCH /systems/{systemId}`.
  Another account can discover public versions and use link-only versions when it already has the
  exact version ID.
- Draft saves, publication and field edits require `expectedRevision`. A `409 stale_revision`
  response includes the latest revision where authorized. Read current state and reconcile first.
  If a draft save times out, read the draft back and compare the document before retrying.
- Retain the exact JSON and `idempotencyKey` for retries of system creation, publication, character
  creation, field edits and inventory changes. Keys are scoped to account and command kind and are shared with the
  corresponding browser commands. Reusing an active key with different input returns
  `409 idempotency_mismatch`. System receipts are replayable for 24 hours, after which a key may
  execute again. Character, roll, push, campaign, invitation, placement, content, template,
  proposal, art, media and scene receipts are replayable for 30 days, after which an expired key
  returns a conflict. Check current state before using a new key after the replay window. Media and
  scene commands require a UUID `idempotencyKey`; others accept up to 128 characters. A replayed
  invitation issue returns `tokenUnavailable: true` instead of the token, so rotate with a new key
  after a lost response.
- Campaign commands use `expectedCampaignRevision`, and invitation, content, template, proposal and
  scene commands use their own `expected…Revision` fields. Placement commands send both the campaign
  and the character revision.
- Resource endpoints require a valid Bearer token. `401` indicates missing or invalid credentials,
  `403 insufficient_scope` a missing scope, `403 forbidden` a campaign role that does not permit the
  command, and `404` covers inaccessible and absent resources. Tokens
  expire after 1–90 days and can be revoked under Account. A revoked token fails the next request.
- A document can use up to 1 MiB after JSON encoding. The HTTP limit is 1 MiB plus 4 KiB for the
  envelope. Image uploads accept up to 8 MiB of JSON for at most 5 MiB of PNG, JPEG or WebP. Other
  writes accept up to 128 KiB. Fog edits carry at most 512 runs. Quotas use fixed one-minute windows
  per account across all tokens and replicas. The overall limit is 120 authorized requests per
  minute, with limits of 12 validations, six publications and 30 uploads. The contract names each
  operation's extra quota in `x-rate-bucket`. Wait for the seconds in `Retry-After` after a `429`.
- Each successful command is recorded in the server log with its operation, account and request ID.
  Request bodies, including invitation tokens and image data, are never logged.
- The character sheet returns stored values, derived values, and validation messages. Creation
  options include each initial field's default and constraints. Resource fields can be set during
  character creation. The single-field edit command accepts ordinary editable fields. Published
  versions are immutable and each character stays pinned to its creation version.
